# 5060 Laptop 8GB：小规模实验结果

状态（2026-10-03）：**单人 200 步、交互 50 步均已完成，无 OOM / NaN；生成质量尚不合格。** 用户授权开始训练后，检查 GPU 已释放再执行。此前的 3 步验证不计作本轮实验结果。这是本次重新复现的新实验，不是原论文实验或历史研究过程。

## 实测结果与边界

| 项目 | 单人 200 步 | 交互 50 步 |
|---|---|---|
| loss / 梯度 / 参数全部有限 | 是 | 是 |
| 有非零梯度的更新数 | 200 | 50 |
| 峰值 PyTorch allocated | 3504.8 MiB | 4268.4 MiB |
| 峰值 PyTorch reserved | 3908 MiB | 4726 MiB |
| 固定训练样本去噪 MSE，前 → 后 | 0.8648 → 0.7114 | 1.1660 → 0.9787 |
| 固定验证样本去噪 MSE，前 → 后 | 1.5966 → 1.4103 | 1.7566 → 1.7091 |

显存是训练期间 PyTorch 的峰值统计，不包含其他程序或全部驱动开销；最大 reserved 约 4.62 GiB。结论仅适用于 batch=1、FP32、120 帧上限的小规模配置，不能外推原论文 batch 或更长动作。

每阶段去噪诊断均取固定的前 4 个 train 和前 4 个 val 样本，在 t=500/900 使用相同随机噪声比较训练前后；单人虽准备了 8 个 val，本项只评估其中 4 个。验证均值分别下降约 11.7% 和 2.7%，样本太少，不能视为泛化或文本语义质量提升的充分证据。优化循环耗时分别约 25.1 秒、9.6 秒，不含初始化、采样、评估、保存和渲染，不能据此推算完整训练耗时。

实际查看同尺度对比图：单人输出仍动作偏小、肢体姿态不自然；双人输出也未形成合理的相对位置与互动。单人验证案例每帧平均关节位移约 0.00273 m，参考动作约 0.03057 m；双人对应为 0.00313 m 与 0.02814 m。这里只衡量运动量，生成动作不必逐点等于唯一参考，不能将位移比例解释成准确率。训练前单人零输出头导致静止；交互阶段的“训练前”已继承本轮训练过的单人主干，不能称作完全随机模型。

这轮证明了原尺寸网络在当前配置下能更新、交互分支有梯度。短训练后的劣质动作还不能归因于 baseline 架构，更不能用来证明需要 RAG。下一步合理候选是先延长同一固定子集的单人训练，检查能否学到自然动作，再扩大数据及交互训练；该后续实验尚未执行。

## 本轮实际遇到的问题

首次交互阶段在载入本轮单人 checkpoint 时失败：scheduler 的学习率元数据含 NumPy 标量，不被 PyTorch 默认 weights-only 加载接受，尚未进入交互更新。修复保存逻辑，将优化器和 scheduler 元数据递归转换为 Python 标量；对已完成的单人 checkpoint 做同样迁移，并逐张量验证模型权重完全不变。随后交互训练成功，保留首次失败日志。这是本轮实验工具兼容问题，不是模型训练不稳定。

最终交互 checkpoint 已用默认 weights-only 方式读取，并在全新模型上通过原生 `nn.Module.load_state_dict(strict=True)` 检查 502 个状态项，无缺失或多余键；采样临时注册的 cfg_model 别名未写入权重。原模型的阶段迁移加载方法用于单人到交互初始化，不能代替交互训练结果的严格重载验证。

## 本轮回答什么问题

先确认原尺寸 baseline 能否在 8GB 上持续更新且不出现 OOM / NaN，再看短训练是否改善去噪，以及采样的人形、运动量与文本动作是否合理。仅看 loss 降低不能证明生成质量。

## 固定设置

| 项目 | 单人阶段 | 交互阶段 |
|---|---|---|
| 原始架构 | 8 层、1024 隐空间 | 同上，保留主干与控制分支 |
| 训练片段 | 32 个 train ID | 上述 ID 中 8 个真实双人片段 |
| 独立验证片段 | 8 个 val ID | 上述 val ID 中 4 个双人片段 |
| 更新次数 | 200 | 50 |
| batch / 精度 | 1 / FP32 | 1 / FP32 |
| 时间长度上限 | 120 帧 | 120 帧 |
| 优化器 | 原始 AdamW、梯度裁剪、按子集 epoch 的 warmup | 同左 |
| 起点 | 已保存的随机单人权重 | 本轮单人权重，不能用随机冻结主干 |

seed=20261003。选样使用官方划分及已记录的缺失资产 / 原始短动作过滤结果。train 和 val ID 不重叠。每个 ID 固定一次个人选择、文本选择及裁剪结果，使用原始数据处理；本轮不持续重采样增强。这是本次新增的小规模优化诊断，不能当作正式论文训练协议。

CPU 检查已通过：单人输入形状为 32×120×262 / 8×120×262，双人为 8×120×524 / 4×120×524，数据全部有限。原始速度计算会少一帧，因此 120 帧裁剪的最大有效长度为 119，其余按原始逻辑 padding；mask 使用真实有效长度。

交互训练仍使用原始数据类返回的场景描述和目标人物描述；生成第二个人的描述从相同原始标注行匹配获得，不给两个人随意套同一句个人描述。

## 执行命令

关闭其他 GPU 密集程序后，在代码重构目录执行：

```powershell
& .\.venv\Scripts\python.exe -u scripts/small_scale_trial.py --stage single --steps 200
& .\.venv\Scripts\python.exe scripts/render_small_scale.py --stage single
```

查看单人结果后，再运行：

```powershell
& .\.venv\Scripts\python.exe -u scripts/small_scale_trial.py --stage multi --steps 50
& .\.venv\Scripts\python.exe scripts/render_small_scale.py --stage multi
```

脚本启动前要求至少 5.5 GiB CUDA 可用显存。该门槛用于避免与其他程序争抢显存，并不能代替实际峰值测试。非有限 loss / 梯度立即报错，不用忽略 NaN 的办法把训练凑完。完成过的阶段不会直接覆盖旧报告。

## 看哪些结果

产物统一放在 `artifacts/small_scale_8gb/`：

- `subset.json` / `subset.npz`：实际样本 ID、描述、有效长度和原始处理后的固定输入。
- `single_progress.jsonl` / `multi_progress.jsonl`：每步 loss、梯度范数、学习率、时间及 PyTorch 显存。
- 阶段 report：固定验证噪声下 t=500/900 的去噪 MSE、训练峰值显存和样例运动量。MSE 是带噪真实动作的恢复误差，不是自由生成与唯一 GT 的“准确率”。
- 阶段 checkpoint：模型、优化器、scheduler 和实验元数据；不是已收敛的论文权重，也不是已有的随机初始化文件。
- `*_comparison.gif`：相同坐标尺度的真实参考 / 训练前 / 训练后动作，没有平滑或逐帧居中掩盖抖动。

`reference_preview.gif` 只有真实数据，验证可视化管线；**不是模型生成效果**。已生成的 `single_train_comparison.gif`、`single_val_comparison.gif`、`multi_train_comparison.gif`、`multi_val_comparison.gif` 从左到右为真实参考 / 训练前 / 训练后。另有静态 PNG 和两阶段训练曲线。动画按源码 FPS=30 的时间假设、隔帧以 15fps 播放。`preparation_report.json` 记录准备阶段的历史状态，当前训练状态以 `single_report.json` / `multi_report.json` 为准。

不在这么小的数据上包装 FID、R-precision 为正式结果。若持续运行稳定但输出仍静止或畸形，应分别记录“显存/数值稳定”和“质量尚不合格”，再决定是否增加训练，而不是直接开始 RAG 改进。
